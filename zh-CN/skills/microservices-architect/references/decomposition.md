# 服务分解和边界

使用领域驱动设计原则识别服务边界的指南。

## 领域驱动设计基础

### 限界上下文识别

**战略模式：**
- **通用语言** - 每个限界上下文都有自己的领域语言
- **上下文映射** - 定义限界上下文之间的关系
- **子域分类** - 核心域、支持域、通用域

**限界上下文指标：**
```
强指标：
- 不同团队拥有不同部分
- 需要不同的发布节奏
- 不同的可扩展性要求
- 不同的技术栈最优
- 清晰的领域模型边界

警告信号：
- 实体在不同上下文中意味着不同的事情
- 同一术语具有不同含义
- 工作流跨越多个聚合
- 团队频繁沟通关于共享数据
```

### 服务边界模式

**数据库驱动分解：**
```
1. 识别聚合（具有不变性的实体）
2. 每个聚合成为服务候选
3. 按事务边界分组相关聚合
4. 服务拥有其数据（无共享数据库）
```

**业务能力分解：**
```
服务按以下组织：
- 用户管理（认证、配置文件、权限）
- 订单管理（购物车、结账、履行）
- 库存管理（库存、仓储、分配）
- 支付处理（交易、退款、对账）
- 通知服务（电子邮件、短信、推送通知）
```

**绞杀植物模式：**
```
单体分解策略：
1. 识别现有代码库中的接缝
2. 一次提取一个服务
3. 通过外观/代理路由流量
4. 逐步迁移功能
5. 安全时废弃旧代码

提取顺序：
1. 从叶子依赖开始（无下游调用）
2. 首先提取支持服务
3. 核心业务逻辑最后
4. 每个服务的数据迁移策略
```

## 服务大小指南

### 微服务特征

**合理大小的服务：**
```
团队指标：
- 2-pizza 团队可以拥有它（5-9 人）
- 单个团队拥有完全所有权
- 如有必要可以在 2-4 周内重写
- 独立的部署管道

技术指标：
- 100-1000 行业务逻辑
- 5-15 个 API 端点
- 1-5 个数据库表
- 启动时间 < 30 秒
- 单一职责关注点
```

**太小（纳米服务）：**
```
警告信号：
- 具有 1-2 个端点的服务
- 过度的网络开销
- 基础设施多于业务逻辑
- 难以跟踪请求
- 服务之间的版本耦合
```

**太大（分布式单体）：**
```
警告信号：
- 多个团队在同一服务上工作
- 冲突的可扩展性要求
- 难以一次性理解
- 长部署时间
- 与其他服务紧密耦合
```

## 康威定律对齐

### 团队结构和服务设计

**团队拓扑：**
```
流对齐团队：
- 拥有端到端服务生命周期
- 与业务能力对齐
- 全栈所有权（从前端到数据库）

平台团队：
- 提供自助服务能力
- 赋能流对齐团队
- Kubernetes、CI/CD、可观察性

赋能团队：
- 帮助复杂实现
- 服务网格设置、安全模式
- 临时辅导角色

复杂子系统团队：
- 专业化领域（ML、搜索、支付）
- 需要深厚的技术专业知识
- 与其他团队的清晰接口
```

## 分解检查清单

### 分解前分析

**业务理由：**
```
检查：
- 需要独立扩展吗？
- 不同团队负责吗？
- 隔离故障可接受吗？
- 频繁的独立部署吗？
- 需要技术多样性吗？

如果大多数为"否" → 首先考虑模块化单体
```

**技术就绪度：**
```
先决条件：
✓ CI/CD 管道已自动化
✓ 监控和警报已就绪
✓ 分布式跟踪能力
✓ 容器编排就绪
✓ 团队具有微服务经验
✓ 清晰的服务所有权模型
```

### 分解步骤

**1. 识别限界上下文：**
```
活动：
- 事件风暴研讨会
- 识别聚合和实体
- 映射业务工作流
- 记录通用语言
- 绘制上下文边界
```

**2. 定义服务契约：**
```
对于每个服务：
- REST/gRPC API 规范
- 事件模式定义
- 数据所有权边界
- SLA 承诺（延迟、可用性）
- 版本控制策略
```

**3. 规划数据迁移：**
```
数据策略：
- 识别共享数据
- 选择一致性模型（最终 vs 强）
- 设计数据同步机制
- 规划模式演进
- 测试回滚场景
```

**4. 提取服务：**
```
实施顺序：
1. 创建新服务骨架
2. 实现业务逻辑
3. 设置数据库（如需要）
4. 添加可观察性（日志、指标、跟踪）
5. 部署到暂存环境
6. 从单体双写（如适用）
7. 切换读取到新服务
8. 从单体移除
9. 生产部署
```

## 要避免的反模式

### 常见错误

**分布式单体：**
```
症状：
- 服务必须一起部署
- 服务之间共享数据库
- 到处都是同步耦合
- 需要版本锁定步调
- 级联故障常见

解决方案：
- 强制每个服务一个数据库
- 使用异步通信
- 独立版本控制 API
- 添加断路器
```

**实体服务：**
```
反模式：
UserService（对 User 实体的 CRUD）
OrderService（对 Order 实体的 CRUD）
ProductService（对 Product 实体的 CRUD）

问题：贫血领域模型，无业务逻辑

更好的方法：
AccountManagement（认证、授权、配置文件）
OrderFulfillment（工作流：购物车 → 支付 → 发货）
ProductCatalog（搜索、推荐、库存）
```

**带有业务逻辑的共享库：**
```
反模式：
common-lib（在所有服务之间共享，包含领域逻辑）

问题：
- 通过依赖紧密耦合
- 强制同步部署
- 违反服务自主权

更好的做法：
- 共享库仅用于技术关注点
- 每个服务重复业务逻辑
- 使用事件保持数据同步
```

## 服务边界验证

### 设计审查检查清单

**服务独立性：**
```
问题：
- 该服务可以独立部署吗？
- 它是否完全拥有其数据？
- 如果依赖服务宕机它能运行吗？
- 团队是否自主进行更改？
- 集成点是否定义良好？
```

**数据所有权：**
```
验证：
- 无共享数据库表
- 清晰的数据所有权边界
- 共享概念的事件驱动同步
- API 提供所有必要数据
- 其他服务无直接数据库访问
```

**运营就绪度：**
```
检查：
- 健康检查端点已实现
- 就绪探测已配置
- 外部调用的断路器
- 分布式跟踪已设置
- 日志带有相关 ID 结构化
- 指标已暴露（Prometheus 格式）
- 文档是最新的
```

## 迁移策略

### 从单体到微服务

**渐进式提取：**
```
阶段 1：准备
- 向单体添加接缝
- 实现 API 层
- 设置监控

阶段 2：提取叶子服务
- 从没有依赖的服务开始
- 示例：通知服务、报告

阶段 3：提取支持服务
- 认证/授权
- 用户管理
- 文件存储

阶段 4：提取核心服务
- 订单处理
- 支付处理
- 库存管理

阶段 5：分解剩余单体
- 渐进式提取
- 最终退役
```

**并行运行模式：**
```
策略：
1. 构建新的微服务
2. 同时运行两个系统
3. 比较输出（影子模式）
4. 逐步转移流量
5. 废弃旧系统

用于：高风险迁移、关键路径
```

## 总结

服务分解既是艺术也是科学。从领域驱动设计开始以识别自然边界，与团队结构对齐，并增量提取。避免过度分解的诱惑。模块化单体比设计糟糕的分布式系统更好。

**关键要点：**
- 限界上下文定义服务边界
- 每个服务一个数据库是不可协商的
- 团队自主权驱动服务设计
- 增量提取，而不是一次性完成
- 可观察性是微服务的先决条件
