## 上下文预算

上下文窗口是稀缺资源 — 即**注意力预算**。每个令牌都会消耗注意力容量。无关令牌会主动降低性能。

**关键指标**：信噪比（SNR）。更高的 SNR = 更好的推理质量。

### 上下文组件

| 组件 | 用途 | 持久性 |
|------|------|--------|
| **系统提示** | 身份、永久规则、输出格式 | 在会话中保持静态 |
| **少样本示例** | 期望行为的演示 | 静态或半静态 |
| **对话历史** | 短期记忆（用户交互） | 每轮增长 |
| **检索上下文（RAG）** | 长期记忆或外部知识 | 每次查询动态变化 |

### 使用 XML 标签结构化上下文

使用明确的分隔符来分离上下文类型。这有助于模型区分指令和数据：

```xml
<instructions>
  You are an expert code reviewer...
</instructions>
<documents>
  <doc id="1" source="auth.py">...</doc>
  <doc id="2" source="models.py">...</doc>
</documents>
<history>
  ...recent conversation turns...
</history>
<query>
  ...current user message...
</query>
```

### 推荐的顺序

1. 系统指令（主要偏见最强）
2. 参考材料（RAG 文档）
3. 少样本示例
4. 对话历史
5. 用户查询（近期偏见最强）

## 上下文退化模式

### 中间丢失问题

**症状**：代理忽略放置在长上下文中间的指令或事实。

**原因**：LLM 表现出首因偏见（对开始部分有强烈关注）和近因偏见（对结束部分有强烈关注）。中间内容获得的关注较少。

**缓解措施**：将关键指令移到开头（系统提示）或在结尾附近重复它们，就在用户查询之前：

```python
# Vulnerable to lost-in-the-middle
prompt = system_prompt + long_history + user_query

# Mitigated: critical instructions repeated near the end
prompt = system_prompt + long_history + instruction_reminder + user_query
```

### 上下文污染

**症状**：先前轮次中的无关或冲突信息混淆了代理，产生矛盾或过时的输出。

**缓解措施**：
- 显式使过时信息失效：*"忽略之前关于 X 的约束；只关注 Y。"*
- 当上下文发生显著变化时，插入清晰的边界标记
- 概括并替换旧的轮次，而不是逐字累积历史

### 分心/稀释

**症状**：太多无关细节降低了推理质量，即使答案存在于上下文中。

**缓解措施**：
- 过滤 RAG 结果，只包含高度相关的文档
- 在注入上下文之前概括冗长的工具输出
- 从历史记录中删除冗余或低信息量的轮次

## 四桶方法

一种管理长期会话上下文的分层策略：

| 桶 | 内容 | 处理方式 |
|----|------|----------|
| **1. 关键指令** | 系统提示、核心约束 | 始终存在、逐字保留 |
| **2. 即时上下文** | 最后 3-5 个对话轮次 | 逐字保留，始终包含 |
| **3. 相关历史** | 语义匹配的过去上下文 | 通过搜索检索（RAG） |
| **4. 归档历史** | 其他所有内容 | 概括或丢弃 |

这可以防止上下文无限增长，同时保留最重要的信息。随着对话长度增加，内容从桶 2 迁移到桶 3 或 4。

## 优化策略

### 上下文压缩

减少令牌使用而不丢失语义含义：

| 技术 | 令牌节省 | 风险 |
|------|----------|------|
| 移除空白 | 少量（1-5%） | 低 |
| 注释/语法剥离 | 中等（10-20%） | 数据风险低，代码风险高 |
| 格式转换（从详细 JSON 到紧凑 YAML/CSV） | 中等（15-30%） | 中等 - 验证可解析性 |
| 历史记录的抽取式概括 | 大量（30-50%） | 中等 - 可能丢失信息 |

### KV 缓存优化

通过在请求之间保持提示前缀恒定来重用静态上下文的计算键值对：

- **静态前缀**：系统指令 + 标准少样本示例（在请求之间不变）
- **动态后缀**：对话历史 + 用户查询（每轮变化）

这允许模型的 KV 缓存跳过静态前缀的重新计算，减少支持提示缓存的 API 的延迟和成本。

### 观察掩码（针对代理）

工具输出相对于其信息内容可能不成比例地大：

| 问题 | 解决方案 |
|------|----------|
| 巨大的工具输出（例如完整的目录列表） | 截断到前 N 行 |
| 冗长的结构化数据 | 概括：*"找到 50 个文件，主要是 .py 文件"* |
| 读取整个文件 | 使用针对性工具（grep、符号查找）而不是 cat |
| 原始 API 响应 | 只提取当前任务需要的字段 |

## 定期重新聚焦

在长期对话（10+ 轮）中，指令遵循度自然会下降。通过定期重新聚焦来解决这个问题：

- 每 5-10 轮，重述当前目标或约束
- 使用明确的检查点：*"确认一下，我们目前正在处理 [目标]。这是正确的吗？"*
- 在主要上下文转换后，插入新方向的摘要

## 退化指标

使用以下指标衡量上下文管理的有效性：

| 指标 | 测试内容 | 如何测量 |
|------|----------|----------|
| **回忆率** | 代理能否从上下文中检索特定事实？ | 在不同位置插入已知事实，查询它们 |
| **指令遵循度** | 在多轮后代理是否仍然遵循约束？ | 在第 5、10、20 轮测试负约束（例如，"不要代码"） |
| **SNR 影响** | 添加上下文是改善还是降低了输出质量？ | 比较有/无额外上下文的准确性 |

## 优化检查清单

- [ ] JSON 键是否描述性强且简短？
- [ ] 系统提示是否没有冗余指令？
- [ ] 是否在只需要函数时发送整个文件？
- [ ] 关键指令是否放置在上下文的开头和/或结尾？
- [ ] 对话历史是否超越了即时窗口进行了概括？
- [ ] RAG 结果在注入前是否经过相关性过滤？
- [ ] 提示前缀是否稳定以支持 KV 缓存重用？
